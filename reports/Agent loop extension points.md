# Contain the hooks before adding more

aidaemon-core's eleven hook points already match or beat the other frameworks on decision semantics, so more hook points are not what it needs. Its typed decisions, rewrite-restarts-judgment rule, a receipt for every call and validated durable transcript edits compare well with all 14 systems surveyed. The real gaps are in operation. A hook panic unwinds the run, a hung hook ignores both cancel and the wall clock, permissive answers beat restrictive ones, and six of the eleven points have no production consumer. Reading the source also turned up a concrete resume defect: a run that ends by cancel, limit or stuck mid-batch keeps its `in_flight` marker, and the daemon would treat it as stranded and drive it again. LangSmith and similar tools can plug in, and OTLP is the right route, but nothing in the daemon exports today. The kernel's `Event` stream also lacks what a model span needs: a start, a model name and a link between parent and child runs. Rank the work as resume integrity, then hook containment, then an observability event contract, then composition and bounds. Do not build a plugin system or an onion middleware layer. All aidaemon claims come from reading commit 612973c, cited as `path:line` (`core/` means `crates/aidaemon-core/src/`, `engine/` means `src/agent/runtime/sdk_engine/`); nothing was built or run.

## Fourteen systems converge on three hook shapes

Agent frameworks use one of three designs, and the choice determines what "which decision wins" can mean. **Wrap-style middleware** (LangChain, Semantic Kernel, Microsoft Agent Framework (MAF), AI SDK model middleware, Pydantic AI's `wrap_*`) gives a layer control of `next`, so it can skip, retry or replace anything inside it. Position decides authority: the outermost layer has the last word ([LangChain](https://docs.langchain.com/oss/python/langchain/middleware/custom), [MAF](https://learn.microsoft.com/en-us/agent-framework/agents/middleware/)). **Verdict-style hooks** (Claude Code, Codex, Goose, OpenHands, MAF Agent Hooks, aidaemon-core) return a constrained decision, which makes composition a fold over decisions. **Staged processors** (Mastra) mutate data and signal through `abort` ([Mastra](https://mastra.ai/docs/agents/processors)). OpenAI's Agents SDK splits the job differently: `RunHooks` return nothing, and control lives in guardrails, approvals and `RunConfig` filters ([lifecycle](https://openai.github.io/openai-agents-python/ref/lifecycle/), [guardrails](https://openai.github.io/openai-agents-python/guardrails/)).

Two claims in the underlying notes need narrowing. It is true of coding agents that no product fully covers typed before-model, after-model and model-failure hooks. It is not true across frameworks: ADK, Pydantic AI and Mastra all cover that ground, and ADK's `on_model_error_callback` can supply a replacement response, which aidaemon's `Fail | Retry` cannot ([ADK](https://adk.dev/plugins/), `core/hook.rs:133-142`). Likewise, `edit_transcript` is not a unique capability. AI SDK's returned `messages` become the base for later steps ([AI SDK](https://ai-sdk.dev/docs/agents/loop-control)), and OpenHands records condensation as an event over an immutable log ([README](https://github.com/OpenHands/software-agent-sdk/blob/v1.60.2/openhands-sdk/openhands/sdk/context/condenser/README.md)). What aidaemon has that those lack is validation at the edit boundary: a malformed replacement is refused and recorded (`core/run_loop.rs:1214-1221`, `:1348-1373`).

## The kernel leads on semantics and trails on operations

**Three design choices are well supported by the failures others report.** Tool-call pairing after trimming or compaction is the most repeated bug class in the corpus, appearing in LangChain ([#38352](https://github.com/langchain-ai/langchain/issues/38352)), ADK ([#7236](https://github.com/google/adk-python/issues/7236)), OpenAI ([#5340](https://github.com/openai/openai-agents-python/issues/5340)), OpenHands ([#4498](https://github.com/OpenHands/software-agent-sdk/issues/4498)) and Mastra ([#24110](https://github.com/mastra-ai/mastra/issues/24110)); these are samples of reports, not a census. Refusing a broken edit addresses that class where it starts, as Pydantic AI's repair at the model boundary does from the other side ([message history](https://pydantic.dev/docs/ai/core-concepts/message-history/)). Restarting all hooks after a rewrite (`core/run_loop.rs:704-733`) closes the gap that MAF handles by issuing a replacement approval request and OpenAI by rechecking after approval ([Agent Hooks](https://learn.microsoft.com/en-us/agent-framework/agents/agent-hooks), [guardrails](https://openai.github.io/openai-agents-python/guardrails/)). The `Indeterminate` receipt for a started non-idempotent call (`core/run_loop.rs:1032-1077`) is the at-most-once-with-unknown-outcome state that AWS and Temporal describe, and no durable engine offers exactly-once ([AWS](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/), [Temporal](https://temporal.io/blog/idempotency-and-durable-execution)). `after_tool` firing on every status, refusals included (`core/run_loop.rs:880-922`), avoids the blind spot apparent in OpenHands, where a code reading suggests hook rejections never reach `PostToolUse`. I found no equivalent of `on_limit` with `Extend` in the pages reviewed: those systems treat limits as configuration, a stop condition or a terminal handler.

**Containment is the sharpest weakness.** Tools are isolated with `catch_unwind`, timeout and cancel. Hooks get bare `.await`s, and the wall-clock bound wraps only `call_model` (`core/run_loop.rs:229`, `:794-803`). A panicking hook leaves `drive` before `finish`, so no `Finished` event and no `on_run_end`. A hung hook blocks indefinitely inside the kernel. Hooks return no `Result` and receive no cancel token (`core/hook.rs:18-37`). Peers are uneven but nearly all have some bound: Agent Hooks denies on exception, timeout or invalid verdict ([spec](https://github.com/responsibleai/agent-hooks/blob/main/spec/0.1/AGENT-HOOKS-0.1.md)), Pydantic AI has per-hook timeouts, Cline isolates plugins in worker threads, and ADK splits control hooks (abort) from error observers (log and continue). A daemon needs this more than a CLI does, because no human is watching a stalled scheduled goal. The daemon may bound this from outside since it polls the run future in a `select!` (`src/agent/runtime/sdk_engine.rs:1453-1476`), but the notes could not establish what catches a panic or stalled turn on interactive channels, so treat that as open.

**Composition lets the permissive answer win.** The first `Extend`, `Retry` or `Continue` short-circuits, while `Stop`, `Fail` and `Accept` merely pass to the next hook (`core/run_loop.rs:1143-1189`, `:310-349`). No policy hook can veto another hook's extension. Claude Code and Codex go the other way and resolve by restrictiveness: `deny` beats everything there, and a Codex `continue: false` beats continuation ([Codex](https://learn.chatgpt.com/docs/hooks)). Registration order is also security-relevant, because `Approve` resumes at `hook_index + 1`, but the kernel enforces it only by convention. Only Pydantic AI, with `get_ordering()`, offers declared ordering constraints ([abstract.py](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/capabilities/abstract.py)).

**On the surface, the honest count is five points, not eleven.** The daemon overrides `before_model`, `before_tool`, `after_tool`, `on_stop` and `on_run_end`. It installs nothing on `on_run_start`, `edit_transcript`, `after_model`, `on_model_error`, `on_limit` or `on_stuck`, and steering, forced `tool_choice` and budgets still live in the provider path (`engine/model_call.rs:190`, `:273`, `:585`). The six newest points have test coverage only. An API surface without a consumer has not met the problems that shape a contract; Cline's partly wired legacy hooks and Codex's parsed-but-unsupported fields show what that looks like once released ([hooks-adapter.ts](https://github.com/cline/cline/blob/main/apps/vscode/src/sdk/hooks-adapter.ts), [Codex](https://learn.chatgpt.com/docs/hooks)).

Some documented behaviour is also wrong. `on_run_end` claims "exactly once" (`core/hook.rs:252`) but fires per segment under plain `run` then `resume`. `crates/EXTENDING.md:101-103` lists five hook points. `DESIGN.md:168-172` says a non-idempotent tool may run twice, which the code contradicts.

## LangSmith plugs in through OTLP, but the event stream is too thin today

Yes, this architecture can feed LangSmith, and the integration pattern is well established. Three routes exist across the field. Native trace processors register with the framework, as with `add_trace_processor()` in OpenAI's SDK, whose docs list about 35 integrations including LangSmith and Langfuse ([OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/)). Client wrapping is what LangSmith documents for the Claude Agent SDK, although its page does not say which mechanism sits underneath ([LangSmith](https://docs.langchain.com/langsmith/trace-claude-agent-sdk)). OTLP is the third, used for Pydantic AI ([LangSmith](https://docs.langchain.com/langsmith/trace-with-pydantic-ai)). A Rust daemon should take OTLP: LangSmith accepts `/otel` with an `x-api-key` header and `Langsmith-Project`, and maps `gen_ai.operation.name`, `gen_ai.tool.name`, `gen_ai.usage.*` and `gen_ai.input.messages` onto runs ([LangSmith OTel](https://docs.langchain.com/langsmith/trace-with-opentelemetry)). Langfuse accepts the same shape at `/api/public/otel`, HTTP only ([Langfuse](https://langfuse.com/integrations/native/opentelemetry)). One exporter therefore serves both, with a small per-backend attribute map: LangSmith reads `langsmith.trace.session_id` and `langsmith.span.kind`, while Langfuse reads `langfuse.session.id` or `session.id` and wants it on every span. I found no reason to write a LangSmith-specific exporter. OpenTelemetry's GenAI conventions remain Development status, so pin a version; they define `invoke_agent` and `execute_tool` spans with `gen_ai.tool.call.id` linkage, and the pages reviewed contain no guardrail, compaction or budget attributes ([agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md), [execute tool](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/execute-tool.md)).

**The sink is the right seam, and the code partly exists.** `aidaemon_policies::TracingSink` already builds `agent_run` and `tool_call` spans (`crates/aidaemon-policies/src/tracing_sink.rs:10-21`). But it appears only in its own tests and exports, the daemon's sink does not use it (`src/agent/runtime/sdk_engine.rs:1204`), and no OpenTelemetry or LangSmith dependency exists in the workspace. Its fields are also not `gen_ai.*`, so an OTel layer on top would produce spans LangSmith cannot type.

A faithful exporter hits concrete holes in `Event` (`crates/aidaemon-core/src/event.rs:15-93`), which this table separates by what each seam can see:

| Needed for a trace | `EventSink` | `Hook` | `Provider` wrapper |
|---|---|---|---|
| Run and turn identity | Yes | Yes | **No**: receives only `ModelRequest` |
| Model span start time | **No start event**; `TurnStarted` precedes hooks | `before_model`, but only sees edits from earlier hooks | Yes |
| Model name | **No** | Yes | Yes |
| Exact request sent | **No** | Only if last in the list | Yes |
| Each provider attempt | **No** | **No** | Yes |
| Timeouts and cancels on a model call | Only via `Finished` | **No**: `on_model_error` is not called | Partly: its future is dropped, so only a drop guard sees it |
| Finish reason or `note` | **No** | `after_model` | Yes |
| Which hook decided, and why | **No**: `Receipt` has reason, not hook identity | Not across hooks | No |
| Tool spans | Yes, with `call_id` and `duration_ms` | Yes | No |
| Parent run of a child | **No** | **No** | No |

No single seam suffices, and that is the actual gap. Claude Code's beta span tree shows the target: an interaction root, `llm_request`, `hook`, and tools split into `blocked_on_user` and `execution`, with subagent spans nested under the parent tool, and content redacted by default ([monitoring](https://code.claude.com/docs/en/monitoring-usage)). The daemon adds a wrinkle: `DaemonProvider` implements only `complete` and owns retries and fallback (`src/agent/runtime/sdk_provider.rs:1-7`), so kernel events see one call where several attempts occurred. Per-attempt spans must originate in that provider path.

Durable runs raise two design constraints. LangSmith silently drops children whose parent is never exported, even after returning `200` ([LangSmith OTel](https://docs.langchain.com/langsmith/trace-with-opentelemetry)), and OTel exports a span when it ends. My inference is that a crash before the root closes would lose that trace, and an interrupted run awaiting an owner could hold a root span open for hours. The safer model is one short root per segment, joined through `langsmith.trace.session_id`, which keeps resume from depending on a live span. Also useful: every event is already journaled with a `created_at` (`crates/aidaemon-store-sqlite/src/lib.rs:156`), so a backfill exporter could rebuild traces after a crash. Finally, exporting to a third party is itself egress of personal content. Default to `NO_CONTENT`, the OTel default ([GenAI spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)), and make content capture an explicit owner setting.

## Ranked gaps and recommendations

Evidence grades here are strict. **Verified** means I or the baseline read it in the code. **Field-backed** means several systems or reported failures converge. **Measured** means numeric studies exist. **Reasoned** means an argument with no measurement behind it.

| Rank | Gap | Recommendation | Effort | Evidence |
|---|---|---|---|---|
| 1 | Terminal runs keep `in_flight`; saved `hook_index` is a raw position | Clear `in_flight` in `finish_batch`; have `stranded_run` check terminal status; persist a hook-chain fingerprint and re-judge from hook 0 on mismatch | Small | Verified by reading; not executed |
| 2 | Hooks have no panic, timeout or cancel containment | Wrap every hook call; add a per-point failure policy and `Event::HookFailed` | Medium | Gap verified; fix field-backed; per-point table reasoned |
| 3 | No exportable model span or decision record | Add model-start and hook-decision events, parent run id, an `OtelSink` with `gen_ai.*` attributes | Medium | Gap verified; OTLP route documented |
| 4 | `on_stop` loops bounded only by run limits; permissive hooks beat restrictive ones | Default consecutive-continuation cap; add a veto variant to limit, retry and stop folds | Small | Field-backed |
| 5 | Standing constraints are exposed to compaction | Keep user constraints in a typed store rendered after every compaction through `before_model` | Medium | Measured, preprints |
| 6 | Six hook points without a consumer; stale docs | Port forced `tool_choice`, budgets and stuck pivots onto them, or mark them unstable | Medium | Verified |
| 7 | No subagent lifecycle; `AgentTool` drops declines and authority | Default `AgentTool` to shared declines and narrowed authority; add tree usage and parent linkage | Medium | Field-backed |
| 8 | `before_model` cannot skip; `on_model_error` cannot recover | Return a decision enum with `Answer`; add `Recover` | Small | Field-backed; demand unproven here |

**Rank 1 is first because it is cheap and acts against the owner.** I traced the first defect directly. The cancel, stuck and limit exits return `BatchEnd` before line 641, `finish_batch` does not clear the marker, and `finish` checkpoints it (`core/run_loop.rs:412-446`, `:641`, `:1272-1307`). `stranded_run` matches on `in_flight.is_some()` with no status check (`engine/recovery.rs:26`), and `drive` then enters `recover`, finds all calls done, and proceeds to another model call. If the daemon's cancel path reaches this code, a run the owner cancelled mid-batch would continue at the start of the next turn; a regression test should confirm that before anything else. OpenHands' reports of a plain message resuming a paused conversation show that class of failure in the field ([#6010](https://github.com/OpenHands/software-agent-sdk/issues/6010)). The second defect is less certain: `memory_hooks` varies in length and sits ahead of the gates (`src/agent/runtime/sdk_engine.rs:1060-1081`, `engine/hooks.rs:118-130`), and resume compares neither hook nor tool lists (`core/agent.rs:204-218`). If the chain shrinks between runs, `Approve` at `hook_index + 1` could skip a gate such as `DispatchGate`. Nobody has reproduced it, but a fingerprint check is a few lines.

**Rank 2 should follow the event, not a global switch.** Enforcers on irreversible effects fail closed, with every instance counted. Observers fail open but record the gap. A stop verifier that breaks must resolve to `AcceptUnmet`, never to success and never to a trap. Claude Code and Goose independently exempt stop hooks from fail-closed for that reason ([Claude Code](https://code.claude.com/docs/en/hooks), [Goose](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/context-engineering/hooks.md)). A failing `edit_transcript` keeps the old transcript. Keep "could not decide" distinct from "allowed", as OpenHands' `success=False` does. No source measures fail-open against fail-closed, so the table is judgment. Timeouts are cooperative in Tokio; MAF documents the same limit for synchronous interceptors, so a blocking hook still cannot be preempted.

**Rank 4 has a known trap.** Claude Code's cap of 8 resets when a tool is called, so it does not bound a hook that keeps provoking tool calls. One user reported a goal hook re-firing about 15 times after a denial ([#98066](https://github.com/anthropics/claude-code/issues/98066)), and another reported 92 denied calls in one Goose run ([#13186](https://github.com/aaif-goose/goose/issues/13186)). Count continuations per run or tie the reset to a new successful receipt, and make any capped exit partial. The daemon's `LedgerStop` already has budgets, so the kernel default mainly protects other SDK users.

**Rank 5 has the strongest numbers in the corpus, though all are recent preprints.** ConstraintRot found 0% violations with full context, 30% after compaction and 0% again with pinning across 1,323 episodes ([arXiv 2606.22528](https://arxiv.org/abs/2606.22528)). ConPACT saw unapproved email deletions in 30 of 100 sessions after compaction and none before, and appending extracted constraints reached over 90% retention ([arXiv 2608.11242](https://arxiv.org/abs/2608.11242)). InflateBench points the other way on loss, finding that summaries rarely dropped instructions but inflated them ([preprint](https://www.researchsquare.com/article/rs-11626292/v1)). aidaemon's tool authority does not depend on transcript memory, so this concerns user standing instructions rather than the kernel's gates.

**Rank 7 is about SDK users more than the daemon.** The daemon wires inheritance itself (`src/agent/runtime/authority.rs:167-198`), but `AgentTool` starts children with no shared declines or narrowing (`crates/aidaemon-agents/src/lib.rs:394-400`). Hooks not reaching subagents recurs in the field ([Claude Code #34692](https://github.com/anthropics/claude-code/issues/34692), [Goose #12650](https://github.com/aaif-goose/goose/issues/12650), [MAF #8050](https://github.com/microsoft/agent-framework/issues/8050)). Whether child token usage rolls up into the daemon's parent run could not be confirmed.

## What remains speculative, and what not to build

Several conclusions are judgment rather than evidence. The notes found no measured comparison of hook composition models, no production data on fail-open incidents, and no adoption data for OTel GenAI conventions. Whether an egress verifier that sees only the request and the call (`src/agent/runtime/untrusted.rs`) resists adaptive attack is untested. It matches Anthropic's stripped-transcript design ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)), but twelve published defenses fell to adaptive attacks ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023)), and an independent benchmark on ambiguous authorization found an 81% miss rate for auto mode ([arXiv 2604.04978](https://arxiv.org/abs/2604.04978)). Keep sink restrictions behind it. A streaming output filter, `on_run_resume`, and a hook-state slot in `RunState` are plausible additions, but no failure in this codebase demands them yet, and the daemon currently uses no kernel streaming. Rank 8 is in the same category.

Three non-goals have firmer support. **Do not load hooks from repositories or config.** The dominant real-world hook vulnerability is a repository file treated as trusted configuration, recurring across Claude Code, Cursor and Gemini CLI, including [CVE-2026-48124](https://github.com/cursor/cursor/security/advisories/GHSA-pc9j-3qc2-95wv) and the [CVE-2026-40068](https://github.com/anthropics/claude-code/security/advisories/GHSA-q5hj-mxqh-vv77) trust bypass. Claude Code's docs state that `-p` and SDK runs treat the folder as trusted ([hooks](https://code.claude.com/docs/en/hooks#workspace-trust)), and a daemon is always in that position. Compiled-in Rust hooks avoid the class entirely; if plugins ever arrive, Codex's hash-pinned review is the model ([Codex](https://learn.chatgpt.com/docs/hooks)). **Do not add onion middleware.** `Provider` wrappers already cover wrap-model, and an onion would make authority positional at the point where the kernel's fold is most auditable. **Do not treat hooks as the security boundary.** Vendors say this themselves: Codex calls tool hooks "a useful guardrail, not a complete enforcement boundary", and shell parsing bypasses recur ([Flatt](https://flatt.tech/research/posts/pwning-claude-code-in-8-different-ways/)). The kernel's typed `EffectKey` model already avoids most of that weakness.

## Conclusion

The survey changes the question. "Which hooks are missing?" has a short answer, while "what happens when a hook misbehaves, a run resumes, or someone needs to see why it decided?" exposes nearly all the risk. The kernel's receipts and durable decisions are the asset that other frameworks struggle to retrofit, and they make observability unusually cheap once `Event` carries a model start, a hook decision and a parent link.

The first useful week is small: a failing test for the cancelled-run re-drive, the `finish_batch` fix, and a hook guard with a typed failure event. An `OtelSink` tested against both LangSmith and Langfuse would then turn silent gate behaviour into something that can be measured, which the current evidence base, here and across the industry, largely lacks.
